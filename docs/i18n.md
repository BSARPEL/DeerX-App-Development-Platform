# Bilingual architecture

[← Documentation](README.md) · [Türkçe](tr/i18n.md)

One setting, `language = "tr" | "en"`, reaches everything: the interface, the
CLI, the live event stream, tool errors, and the instructions and tool
descriptions the **model itself** reads.

```toml
[deerx]
language = "en"
```

```bash
DEERX_LANGUAGE=en uv run deerx status     # for one invocation
```

In the web interface there is a **TR / EN** switch in the top bar. It
changes the client and writes the setting to the server in one click, so
the event stream does not stay in the old language.

## The four catalogs

| Where | What it covers | Size |
|---|---|---|
| `web/static/i18n.js` | Everything rendered in the browser | 569 keys × 2 |
| `i18n.py` | Everything from the server: events, errors, CLI | 466 keys × 2 |
| `tools/descriptions_en.py` | Tool and parameter descriptions | 39 tools |
| `agents/prompts/en/` | Agent instructions | 13 prompts |

Four rather than one because they resolve at different times and in different
places — the browser has no access to the Python catalog, and the model-facing
text is prose that belongs next to what it describes.

## Why the model-facing side matters

Running an English prompt with Turkish tool descriptions gives the model a
two-language context: its instruction in one language, the description of every
tool in its hand in another. Tool *errors* are the same — an agent working in
English used to receive "Aranan metin 3 kez geciyor" and have to work out what
went wrong.

This is not cosmetic. It is context quality.

## Where the text lives, and why

**Interface text** resolves on the client. `app.js` calls `t("phase." + id)`, so
the server sends ids and the browser renders names.

**Server text** resolves in `i18n.py`:

```python
from .i18n import t
raise ToolError(t("fs.not_unique", count=count))
```

A missing key returns the key itself — a missing translation becomes visible
without crashing anything.

**Tool descriptions** are the deliberate exception. The Turkish stays inline on
the tool class, because that is where the behaviour is documented and pulling it
out would leave the class unreadable. The English lives in `descriptions_en.py`,
and `Tool.spec()` overlays it:

```python
override = ENGLISH.get(self.name, {}) if language() == "en" else {}
return {
    "name": self.name,
    "description": (override.get("") or self.description).strip(),
    "input_schema": _with_descriptions(self.schema, override),
}
```

The schema is **copied**, not mutated. It is a class attribute — mutating it
would freeze the language for the whole process at the first `spec()` call.

**Agent prompts** are files, looked up in this order:

```
workspace/prompts/<role>.md   →   package prompts/<lang>/<role>.md   →   package prompts/<role>.md
```

So a workspace override wins over both languages, and Turkish is the fallback.

## Two things that stay untranslated on purpose

**Artifact file names.** `analiz-raporu.md`, `mimari.md`,
`gelistirme-plani.md` are Turkish in both languages, because
`PHASE_DELIVERABLE` matches a phase's deliverable by name. Translating them
would break the check that a phase produced anything.

**`Phase.stage`.** It returns `"Anlama"` / `"Tasarım"` / `"Üretim"` /
`"Teslim"` — and those are **identifiers**, not display text. `app.js` looks
them up as `t("stage." + name)`. Translating server-side would make the English
interface display the key. The property carries a comment saying so.

The distinction generalises: a string the client uses as a **key** must not be
translated on the server. `phase.label` and `agent_label` are safe because the
client resolves those by phase id and ignores the server's values.

## The CLI is a special case

Typer builds help text from decorators — at **import time**, before any
configuration is read. So the language has to be decided before the module body
runs:

```python
def _early_language() -> str:
    for name in ("DEERX_LANGUAGE", "DEERX_LANG"):
        if value := os.environ.get(name):
            return value
    # ... then read deerx.toml directly
    return "tr"

set_language(_early_language())

app = typer.Typer(help=t("cli.app"), ...)
```

Reading the config here is deliberately tolerant: a broken `deerx.toml` falls
back to Turkish rather than raising. A CLI that cannot be *imported* because its
config file is malformed is a CLI that cannot run the command you would use to
fix it.

### The environment variable has to win

`DEERX_LANGUAGE` overrides `deerx.toml`, which is the opposite of every other
setting. The reason is that the CLI's help can only see the environment
variable. If the file won at runtime, `DEERX_LANGUAGE=en deerx init` would print
English help and a Turkish panel — worse than either language alone.

An explicit override in code still beats the environment variable:

```
overrides  >  DEERX_LANGUAGE  >  deerx.toml  >  "tr"
```

## What the tests hold down

Translation is not a one-time job. The next feature brings a new message, and
routing it through the catalog is easy to forget — the interface is English, the
new message is Turkish, and nothing crashes to reveal it.

| Test | What it catches |
|---|---|
| `test_no_hardcoded_turkish.py` | Any user- or model-facing string bypassing the catalog |
| Catalog shape | A key present in one language and missing in the other |
| Placeholder parity | `{name}` in Turkish but not in English — silently dropped information |
| No Turkish letters in English | A half-finished translation |
| Messages actually switch | The catalog being right while the call site is still hardcoded |
| Phase label parity | A phase added to one catalog but not the other |
| CLI help in a subprocess | That the import-time chain really works |
| Tool descriptions | Every tool and every parameter has both, and the schema is not mutated |

`test_no_hardcoded_turkish.py` walks the AST and inspects the string arguments
of calls that reach a user or a model: `ToolError`, `_error`, `console.print`,
`events.emit`, `log.warning` and so on.

It also **tests itself**. A scanner whose patterns were deleted, or whose root
path was wrong, would report every file clean and the suite would stay green
while covering nothing.

That was not hypothetical: the scanner did not descend into list literals, so
`console.print("\n".join([...]))` slipped past it — and the two blocks it missed
were the setup-token message and the refusal to expose an unauthenticated server
to a network. The first two things a user sees.

## Adding a language

Nothing in the design assumes two:

1. Add the code to `SUPPORTED` in `i18n.py` and fill in every key.
2. Add the same keys to `static/i18n.js`.
3. Add `agents/prompts/<code>/`.
4. Add a column to `descriptions_en.py` — or, more honestly at that point,
   restructure it into a per-language mapping.

The catalog-shape tests will tell you exactly what is missing.
